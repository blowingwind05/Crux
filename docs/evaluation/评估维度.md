# Crux 评估指标总览

## 1. Understanding — 意图解析评估

| 指标 | 类型 | 说明 |
|------|------|------|
| `intent_accuracy` | 数值 0/1 | `user_goal` 字段是否与期望完全一致 |
| `constraint_precision` | 0.0–1.0 | 结构化约束的精确率 |
| `constraint_recall` | 0.0–1.0 | 结构化约束的召回率 |
| `constraint_f1` | 0.0–1.0 | 约束的 F1 综合分 |
| `constraint_exact_match` | bool | 约束集合是否完全匹配 |
| `sparse_keyword_precision/recall/f1` | 0.0–1.0 | 稀疏检索关键词的精确率/召回率/F1 |
| `dense_query_precision/recall/f1` | 0.0–1.0 | 稠密检索查询的精确率/召回率/F1 |
| `invalid_constraint_field_count` | 整数 | Schema 之外的非法约束字段数量（必须为 0 才能通过） |
| `latency_ms` | 毫秒 | 模块执行耗时 |

**LLM 评分维度**

| 维度 | 说明 |
|------|------|
| `intent_alignment` | 意图对象是否正确捕捉了用户目标 |
| `constraint_semantics` | 约束语义是否等价（允许措辞差异） |
| `retrieval_plan_quality` | 检索计划的合理性 |
| `rubric_quality` | 评判标准（rubric）的质量 |

**通过条件**：`llm_overall_score ≥ 阈值`（默认 0.75）且 `pass_recommendation = true` 且 `invalid_constraint_field_count = 0`

---

## 2. Retrieval — 检索质量评估

| 指标 | 类型 | 说明 |
|------|------|------|
| `recall_at_k` | 0.0–1.0 | Top-K 内相关文档的召回率 |
| `precision_at_k` | 0.0–1.0 | Top-K 内的精确率 |
| `mrr` | 0.0–1.0 | Mean Reciprocal Rank，第一个相关结果的排名倒数均值 |
| `ndcg_at_k` | 0.0–1.0 | Normalized Discounted Cumulative Gain，考虑排名位置的质量分 |
| `retrieved_count` | 整数 | 实际返回的文档数量 |
| `latency_ms` | 毫秒 | 模块执行耗时 |

**LLM 评分维度**

| 维度 | 说明 |
|------|------|
| `topk_relevance` | Top-K 文档的整体相关性 |
| `ranking_quality` | 排序是否将最相关文档置于前列 |
| `coverage_of_need` | 检索结果对信息需求的覆盖程度 |
| `constraint_alignment` | 结果是否满足查询中的过滤约束 |

**通过条件**：`llm_overall_score ≥ 阈值`（默认 0.70）且 `pass_recommendation = true` 且 `recall_at_k ≥ min_recall_at_k`

---

## 3. Adjudication — 证据判定评估

| 指标 | 类型 | 说明 |
|------|------|------|
| `relevance_accuracy` | 0.0–1.0 | (TP + TN) / 候选文档总数，整体判定准确率 |
| `relevance_precision` | 0.0–1.0 | 被接受文档中真正相关的比例 |
| `relevance_recall` | 0.0–1.0 | 相关文档中被正确接受的比例 |
| `relevance_f1` | 0.0–1.0 | 精确率与召回率的调和均值 |
| `evidence_quality` | 0.0–1.0 | 抽取证据与黄金标准的文本重叠 F1 |
| `acceptance_rate` | 0.0–1.0 | 被接受文档占候选文档的比例 |
| `latency_ms` | 毫秒 | 模块执行耗时 |

**LLM 评分维度**

| 维度 | 说明 |
|------|------|
| `relevance_decision_quality` | 接受/拒绝决策的语义合理性 |
| `evidence_quality` | 提取证据的质量（允许同义改写） |
| `rejection_quality` | 被拒绝文档的判断是否合理 |
| `rubric_alignment` | 判定是否符合 intent 中的评判标准 |

**通过条件**：`llm_overall_score ≥ 阈值`（默认 0.75）且 `pass_recommendation = true` 且 `relevance_accuracy ≥ min_relevance_accuracy`

---

## 4. Strategy — 缺口分析评估

| 指标 | 类型 | 说明 |
|------|------|------|
| `gap_detection_accuracy` | 0/1 | `gap_analysis_result` 是否与期望状态完全一致（`insufficient` / `sufficient`） |
| `missing_precision` | 0.0–1.0 | 预测缺失信息中真正缺失的比例 |
| `missing_recall` | 0.0–1.0 | 真实缺失信息中被正确识别的比例 |
| `missing_f1` | 0.0–1.0 | 缺失信息识别的 F1 分 |
| `coverage_score` | 0.0–1.0 | 模块自评的证据覆盖度 |
| `coverage_error` | 浮点数 | 实际覆盖度与期望覆盖度的绝对误差 |
| `latency_ms` | 毫秒 | 模块执行耗时 |

**LLM 评分维度**

| 维度 | 说明 |
|------|------|
| `gap_decision_quality` | 充足/不足决策的语义合理性 |
| `missing_info_quality` | 识别出的缺失信息是否准确 |
| `suggested_query_quality` | 建议的后续查询是否合理有效 |
| `coverage_assessment_quality` | 覆盖度评估的准确性 |

**通过条件**：`gap_detection_accuracy = 1.0`（状态必须完全一致）且 `llm_overall_score ≥ 阈值`（默认 0.75）且 `pass_recommendation = true`

---

## 5. Pipeline — 端到端评估

| 指标 | 类型 | 说明 |
|------|------|------|
| `total_latency_ms` | 毫秒 | 完整 pipeline 执行耗时 |
| `iteration_count` | 整数 | 实际执行的搜索迭代轮次 |
| `trace_stage_count` | 整数 | trace 中记录的阶段总数 |
| `trace_completeness` | 0.0–1.0 | 每个 stage 均有 input/output/duration 的比例 |
| `final_evidence_recall` | 0.0–1.0 | 最终证据集对期望文档的召回率 |
| `report_present` | bool | 最终报告是否生成 |
| `gap_path_accuracy` | 0/1 | 实际迭代路径（sufficient/insufficient 序列）是否与期望完全一致 |

**LLM 评分维度**

| 维度 | 说明 |
|------|------|
| `goal_satisfaction` | pipeline 整体是否满足了用户目标 |
| `report_quality` | 最终报告的质量 |
| `evidence_support` | 报告结论是否有证据支撑 |
| `iteration_strategy` | 迭代次数和策略是否合理 |
| `trace_coherence` | 执行 trace 的连贯性与完整性 |

**通过条件**：`report_present = true` 且 `gap_path_accuracy = 1.0` 且 `trace_completeness = 1.0` 且 `llm_overall_score ≥ 阈值`（默认 0.75）且 `pass_recommendation = true`（Pipeline 是五个模块中通过条件最严格的）
